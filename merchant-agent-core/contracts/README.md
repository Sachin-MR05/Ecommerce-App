# Communication Contract

The Communication Contract is the JSON wire protocol between the **Merchant
Agent Core** (Python) and the **Java Tool Layer**. It is data definitions
only - `ToolRequest`, `ToolResponse`, `ToolError` - with no execution,
reasoning, HTTP client, or database logic anywhere in it.

```
Agent Core  --ToolRequest-->  [ HTTP boundary ]  --> AgentToolRegistry --> AgentTool --> MerchantCommerceAdapter --> Existing Backend
Agent Core  <--ToolResponse--  [ HTTP boundary ]  <-- AgentToolRegistry <-- AgentTool <-- MerchantCommerceAdapter <-- Existing Backend
```

## Why this exists, and why it's separate from the Tool Layer

`AgentTool` / `AbstractAgentTool` / `AgentToolRegistry` already define how a
tool call executes *inside* the Java process. That's an execution
concern. What crosses the network between two different languages and
processes is a *protocol* concern, with its own rules (stable field
names, explicit nulls, no coupling to either side's internal types). Mixing
the two would mean any internal refactor of `AgentTool` risks silently
breaking the Python client, and vice versa. Keeping the contract as its own
package makes the wire shape the thing both sides agree to hold stable,
independent of how each side is implemented internally.

This is also why `contract.ToolRequest`/`ToolResponse` are **not** the same
classes as `com.ecommerce.tools.model.ToolRequest`/`ToolResponse`:

| | `tools.model.ToolRequest`/`ToolResponse` | `tools.contract.ToolRequest`/`ToolResponse` |
|---|---|---|
| Scope | In-process, `AgentTool.execute(...)`'s parameter/return type | Cross-process, the HTTP wire shape |
| Shape | `userId` + a flat `parameters` map | `requestId`, `toolName`, `arguments`, `context` / `requestId`, `success`, `result`, `error` |
| Owner | Tool Layer execution (`AbstractAgentTool`, concrete tools) | This contract |

The HTTP boundary (`AgentToolController`) is the one place that translates
between them. Neither the contract nor the tools know about the other's
shape.

## What each type represents

### `ToolRequest`

One tool call, from Agent Core to the Tool Layer.

| Field | Type | Required | Nullable | Notes |
|---|---|---|---|---|
| `requestId` | string | yes | no | Unique per call, generated by the Agent Core. Echoed back unchanged on the response for correlation/tracing. |
| `toolName` | string | yes | no | Canonical tool name (e.g. `search_products`). Not enumerated by the contract - new tools need no contract change. |
| `arguments` | object | no (defaults to `{}`) | no | Tool-specific parameters. Opaque to the contract - only the target tool's own input schema gives these meaning. |
| `context` | object | no (defaults to `{}`) | no | Optional, extensible execution metadata. Conventional keys in use today: `userId`, `sessionId`, `conversationId`, `tenantId`, `locale`, `currency`. No fixed schema is enforced - see "Why context is a plain map" below. |

### `ToolResponse`

The Tool Layer's answer to one `ToolRequest`.

| Field | Type | Required | Nullable | Notes |
|---|---|---|---|---|
| `requestId` | string | yes | no | Must match the originating request's `requestId`. |
| `success` | boolean | yes | no | Whether the tool executed successfully. |
| `result` | any | no | yes | Arbitrary structured tool output. Present when `success` is `true`, `null` when `false`. The contract makes no assumption about its shape - it does not assume every tool returns e.g. a `products` list. |
| `error` | `ToolError` | no | yes | Present when `success` is `false`, `null` when `true`. |

### `ToolError`

A standardized description of what went wrong - never business logic, never a decision about what to do next.

| Field | Type | Required | Nullable | Notes |
|---|---|---|---|---|
| `code` | string | yes | no | Specific, tool/domain-level identifier (e.g. `PRODUCT_NOT_FOUND`). Free-form by design - not enumerated by the contract, since new tools introduce new specific failures. |
| `message` | string | yes | no | Human/LLM-readable explanation. |
| `type` | enum | yes | no | Coarse category - see below. What a caller branches on generically. |
| `details` | object | no (defaults to `{}`) | no | Optional, arbitrary structured context (e.g. `{"productId": 42}`). |

**Allowed `type` values** (deliberately small - add one only when an entire
class of callers needs to treat it differently, not per failure mode):

```
VALIDATION_ERROR
NOT_FOUND
UNAUTHORIZED
FORBIDDEN
INVENTORY_UNAVAILABLE
PAYMENT_REQUIRED
TOOL_EXECUTION_ERROR
TIMEOUT
INTERNAL_ERROR
```

### Why `context` is a plain map, not a typed object

The spec lists `userId`/`sessionId`/`conversationId`/`tenantId`/`locale`/
`currency` as *examples* of what it may contain, and explicitly says "keep
this extensible" and "do not put business logic inside the context
object." A fixed set of typed fields would need a contract change every
time a new cross-cutting concern (an experiment flag, a channel identifier,
a trace id) needs to ride along - a plain, documented-by-convention map
avoids that, at the cost of no compile-time typo protection. That trade
was made deliberately in favor of extensibility.

## JSON wire format

### Request

```json
{
  "requestId": "req-123",
  "toolName": "search_products",
  "arguments": {
    "query": "laptop",
    "maxPrice": 50000
  },
  "context": {
    "sessionId": "session-456",
    "currency": "INR"
  }
}
```

### Successful response

```json
{
  "requestId": "req-123",
  "success": true,
  "result": {
    "products": []
  },
  "error": null
}
```

### Error response

```json
{
  "requestId": "req-123",
  "success": false,
  "result": null,
  "error": {
    "code": "INVENTORY_UNAVAILABLE",
    "message": "Product is currently unavailable",
    "type": "INVENTORY_UNAVAILABLE",
    "details": {}
  }
}
```

`result`/`error` are always present as explicit `null` on the side that
doesn't apply (not omitted) - both the Pydantic models (default
serialization, no `exclude_none`) and the Jackson models (no
`@JsonInclude(NON_NULL)`) produce this shape by default, so no extra
config is needed on either side to keep them aligned.

## Examples for four tools

**`search_products`** (arguments are the search filters; result is a list):

```json
// request
{ "requestId": "req-1", "toolName": "search_products",
  "arguments": { "query": "laptop", "category": "electronics" }, "context": {} }
// response
{ "requestId": "req-1", "success": true,
  "result": { "products": [{ "id": "P1001", "name": "Laptop", "price": 49999 }] }, "error": null }
```

**`get_product`** (single id in, single object out):

```json
{ "requestId": "req-2", "toolName": "get_product", "arguments": { "productId": "P1001" }, "context": {} }
{ "requestId": "req-2", "success": true, "result": { "id": "P1001", "name": "Laptop" }, "error": null }
```

**`check_inventory`** (result shape is nothing like a product list):

```json
{ "requestId": "req-3", "toolName": "check_inventory",
  "arguments": { "productId": "P1001", "quantity": 2 }, "context": {} }
{ "requestId": "req-3", "success": true,
  "result": { "productId": "P1001", "requestedQuantity": 2, "availableQuantity": 1, "available": false }, "error": null }
```

**`add_to_cart`** (a user-scoped tool - `userId` travels in `context`, not `arguments`):

```json
{ "requestId": "req-4", "toolName": "add_to_cart",
  "arguments": { "productId": "P1001", "quantity": 1 }, "context": { "userId": 42, "sessionId": "session-456" } }
{ "requestId": "req-4", "success": false, "result": null,
  "error": { "code": "INSUFFICIENT_STOCK", "message": "Only 1 unit(s) available", "type": "INVENTORY_UNAVAILABLE", "details": {} } }
```

None of these four required a contract change to support - that's the
point of `arguments`/`result` staying opaque.

## Responsibility boundaries

| Component | Owns |
|---|---|
| Agent Core | Reasoning, tool selection, conversation/agent state, constructing `ToolRequest`, interpreting `ToolResponse` |
| Communication Contract | The wire shape only - validation of its own fields, JSON (de)serialization |
| Tool Layer (`AgentToolRegistry`/`AgentTool`) | Discovering and executing tools, translating between the contract and its own internal `tools.model` types |
| Merchant Adapter | Integration with the existing ecommerce backend |
| Existing Backend | Database, payment, inventory, orders |

The contract itself never calls a tool, accesses a database, calls an API,
performs agent reasoning, or contains authentication/payment/inventory
implementation. Both `ToolRequest.py`/`.java` reject a request that's
missing `requestId`/`toolName` (or has an empty `toolName`) at construction
time - that's protocol-shape validation, not business validation, and it's
the only kind of validation these classes do.

## How a future tool uses the contract without changing it

Adding `track_order` or `cancel_order` requires zero changes here:

1. The Java side adds a new `AgentTool` (as already established) with its
   own name/schema.
2. The Agent Core builds a `ToolRequest` with `toolName: "track_order"` and
   whatever `arguments` that tool's schema calls for.
3. The Tool Layer executes it and returns a `ToolResponse` whose `result`
   shape is whatever `track_order` naturally returns - a delivery status
   object, not a product list.

Nothing about `ToolRequest`/`ToolResponse`/`ToolError` needed to know
`track_order` would exist.

## Versioning

**Decision: no `contractVersion` field for now.** Reasoning:

- Both sides of this contract are deployed together, by the same team, as
  part of one system - there's no independent third party consuming this
  protocol yet, and no scenario today where Python and Java would run two
  different contract versions against each other.
- A version field with no version-handling logic anywhere (no code branches
  on it) is dead weight - it would be over-engineering for a protocol with
  a single consumer and a single producer, which the brief explicitly warns
  against.
- The contract is already designed to evolve without breaking changes for
  the common case: new tools need no contract change (see above), and new
  *optional* fields can be added to any of the three types without
  breaking existing callers, since both Pydantic and Jackson ignore unknown
  fields and treat missing optional fields as absent/default.

**When to introduce it:** the moment this contract is consumed by a party
this team doesn't fully control the release of - a third-party agent
integration, a separate deployable Agent Core version, or a public API.
At that point, add a required `contractVersion` (or `"v1"` in the URL
path, e.g. `/v1/tools`) and start enforcing compatibility rules across
versions. Don't add it speculatively before that's true.

## Tests

- **Python** (`tests/test_tool_request.py`, `test_tool_response.py`,
  `test_tool_error.py`): valid construction, each required-field-missing
  case, empty-string rejection, default handling for `arguments`/`context`/
  `details`, arbitrary nested shapes, JSON serialization (`by_alias=True`)
  matching the exact wire format above, and JSON deserialization including
  a malformed/missing-field rejection case.
- **Java** (`ToolRequestTest`, `ToolResponseTest`, `ToolErrorTest`): the
  same cases via Jakarta Bean Validation (`Validator.validate(...)`) for
  required-field enforcement, and Jackson `ObjectMapper` round-trips
  asserting the exact same field names/shape as the Python tests assert
  against - this is how the two are checked against each other, since the
  two codebases can't literally import one shared fixture.

## Assumptions / compatibility notes

- **This contract is not yet wired into `ToolClient`/`AgentToolController`.**
  Those currently speak an earlier, simpler ad hoc shape (`{"arguments":
  ...}` in, `{"success", "data", "errorCode", "errorMessage"}` out). Adopting
  this contract as the actual wire format requires a follow-up change to
  both: `ToolClient.execute_tool()` to build/parse `contracts.ToolRequest`/
  `ToolResponse`, and `AgentToolController` to accept/produce
  `contract.ToolRequest`/`ToolResponse` and translate to/from
  `tools.model.ToolRequest`/`ToolResponse` when calling
  `AgentToolRegistry`. That integration was left out of this change
  deliberately - the brief scoped this task to "the contract only," and
  the integration is a separate, reviewable change.
- `context.userId` is still just a map entry at the contract level, not an
  authenticated value - whatever consumes it (the HTTP boundary, when the
  integration above happens) must still resolve/validate it from an
  authenticated session rather than trusting it as given, exactly as noted
  for the earlier `AgentToolController` draft.
